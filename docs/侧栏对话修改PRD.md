# 画布侧栏「对话修改」开发需求 PRD

版本：v0.1

日期：2026-09-21

状态：需求评审稿；核心入口和布局已确认，扩展交互与默认参数待评审。

交付范围：本文件定义开发需求，不代表功能已经实现或已获准部署。

## 1. 产品目标

在画布右侧提供对话式图片编辑入口。用户选择编辑模式、指定图片、输入修改要求，得到结果后可继续修改；同一对话中保留各轮输入、指令和输出，便于查看与比较。

典型使用过程：选择一张服装效果图 → 输入「将衣服改为深蓝色」→ 查看结果 → 以该结果继续修改 → 输入「只调整袖口」。用户也可选择多图融合，或通过蒙版指定局部修改区域。

本功能面向现有桌面画布用户，不限定于「一键换装」模板。

### 2.1 第一版范围建议

完成三种模式的图片输入、提交、结果展示、多轮继续修改及必要的异常恢复。复用现有图片上传、素材选择、图片查看、对比、下载、蒙版编辑和任务队列能力。

以下不纳入第一版：历史会话列表、自由聊天问答、联网搜索、自动选择编辑模式、自动串行执行多步编辑、语音输入、视频编辑、多人协作对话、会话分享、分支树可视化。用户明确要求的一轮多方案生成属于本期范围，不属于自动多步编辑。现有节点编辑和工作流仍保持可用。

## 3. 入口与侧栏布局

### 3.1 入口及展开行为

- 「对话修改」按钮与「属性」按钮纵向排列，沿用现有右侧按钮的视觉风格、尺寸体系和提示方式。
- 已确认：普通点击或拖动画布中的其他图片不切换对话。选中另一张图片 B 后点击「对话修改」，展开或切换到 B 的对话，并保留原对话 A 的未发送草稿。
- 当按钮所指图片与当前对话一致时，点击展开，展开后再次点击收起；所指图片属于另一对话时，点击优先切换，不误作收起。
- 已确认：画布同时选中多张图片后点击「对话修改」，先展示具体图片供用户指定一张作为对话起点，不默认取第一张、不自动切换到多图融合、不自动加入其余选中图片。选择完成后按既有图片来源规则定位或建立对话；若涉及同一对话更换底图，仍遵守草稿确认规则。取消选择不改变当前对话或草稿，整个选择过程不触发生成。
- 已确认：未选中图片时入口仍可用。有当前项目的当前对话则恢复该对话及按本页规则保留的草稿，不要求重新选择画布图片；没有当前对话则展示选图空状态，提供本地上传、素材库入口以开始新修改。选图完成前不能发送；仅打开空状态不创建生成任务，也不自动选择其他项目的对话。这里的恢复不增加刷新后恢复未发送草稿的承诺。
- 从属性面板切换到对话面板时，仅替换右侧内容；返回属性时继续展示当前所选节点的属性。
- 收起或切换面板不删除对话、不清空输入、不取消已提交任务。
- 打开侧栏不得重建画布或清空节点选择；调整可视区域时不主动执行 fitView，不改变用户已有的缩放与位置。

### 3.2 布局草图

```text

                                    ┌────────────────────────────┐
右侧入口：                           │ 对话修改              收起 │
  [属性]                            ├────────────────────────────┤
  [对话修改]                        │ 单图修改│多图融合│局部重绘 │
                                    ├────────────────────────────┤
                                    │ 当前对话历史               │
                                    │ 本轮图片 + 用户修改指令    │
                                    │ 运行状态 / 生成结果         │
                                    │ 查看、对比、下载、继续修改 │
                                    │ ……独立滚动……              │
                                    ├────────────────────────────┤
                                    │ 本轮底图 / 有序参考图片     │
                                    │ 蒙版入口（局部重绘模式）   │
                                    │ 修改指令输入框             │
                                    │ 参数入口（建议）    [发送] │
                                    └────────────────────────────┘
```

已确认采用占位式右侧栏，打开时收窄画布可视区域，不以浮层覆盖画布；展开、收起或切换属性面板均保持画布当前缩放与位置，不主动执行 fitView 或居中。对话区可能需要比当前 320px 属性栏更宽；具体宽度与折行方式通过 1024、1280、1440 CSS 像素桌面 UI 稿验证后确定，不将草图比例当作像素要求。

### 3.3 桌面与可访问性要求

- 支持 1024、1280、1440 CSS 像素窗口宽度；不增加移动端布局。
- 输入区固定在面板底部，历史独立滚动；长指令、图片和按钮不得引起页面横向溢出。
- 模式名称不得因缩窄而无法辨认；需要折行时保持选中状态清晰。
- 标准控件使用项目本地 shadcn 组件，颜色与主题继承 `--gc-*`。
- 按钮具备可访问名称和展开状态；模式选择支持键盘操作及可见焦点。
- 建议 Enter 换行、Ctrl/Cmd + Enter 发送；输入法组合输入期间不发送。
- Escape 优先关闭当前蒙版/图片弹层，再处理侧栏；侧栏关闭后焦点返回入口。
- 尊重系统减少动态效果设置，禁用对应滑出动画。

## 4. 三种编辑模式

### 4.1 共同规则

每次发送形成一轮编辑，必须包含明确的模式、有效的输入图片、非空修改指令及合法参数。只有点击发送或执行等价键盘操作才提交生成；选图、切换模式、绘制蒙版和查看历史不触发生成。

图片来源已确认：本地上传、素材库、当前画布中的具体图片、当前对话中的成功结果。画布节点有多张输出时需选择具体图片，不默认取全部输出。用户切换画布选中节点，不得静默替换已放入输入区的图片。

选图入口明确区分「开始新修改」与「添加参考图」。从本地上传或素材库选图并明确「开始新修改」时，以所选图片新建独立图片对话，不自动定位或合并旧对话，也不继承旧对话的有效要求；原对话的各模式未发送草稿按本页保留规则保留。作为参考图添加时，图片仅加入当前模式输入，留在当前对话，不改变对话归属；仍须满足该模式的数量与能力限制。两种操作均不自动发送生成请求。新修改起点的创建不同于在同一对话中更换历史底图，不清空原对话草稿。

输入区显示图片缩略图、顺序编号及必要的底图标识；发送时保存图片引用和顺序快照，历史显示使用当轮快照，不跟随源节点后续变化。

### 4.2 单图修改

- 恰好选择一张图片，配合文本指令提交。
- 支持替换图片与移除图片；图片为空时提示添加图片。
- 不携带蒙版，也不悄悄传入上轮的额外参考图。
- 示例：「将上衣改为深蓝色，保留人物、裤子和背景。」

### 4.3 多图融合

- 已确认：融合归属发起编辑的图片对话。参考图不合并各自历史，融合输出在该对话中继续迭代；调整当轮参考图顺序不改变对话归属。
- 至少选择两张图片，按图 1、图 2……明确编号。
- 用户可调整顺序或删除图片，界面顺序必须与服务器提交顺序一致。
- 示例：「将图 1 的人物放入图 2 的场景，采用图 3 的色彩。」
- 调序后不自动改写用户输入的图号；发送前始终可看到最终编号对应关系。
- 第一版采用现有通用编辑的 8 张上限，计入本轮全部输入图片；不得按「底图 + 8 张参考图」计算。用户提供的 API 文档允许最多 16 张，本功能当前采用的产品上限为 8 张。

### 4.4 mask 局部重绘

- 明确指定一张底图，打开已有蒙版编辑能力，涂抹希望修改的区域，再填写修改要求。
- 未提供有效底图、未完成蒙版或指令为空时，不可提交，给出具体缺失原因。
- 蒙版绑定底图的具体图片引用/版本；换底图或选用新的历史结果后，旧蒙版失效，必须重新绘制。
- 提交给上游的 mask 对应第一张图片，使用带 alpha 的 PNG，与实际提交底图尺寸一致，文件小于 4 MiB；由服务端校验和必要预处理保证。
- 用户所见涂抹表示「希望修改的位置」，内部 alpha 转换由系统完成。
- 复用现有区域引导、扩展与合成策略；不得仅凭上游文档承诺涂抹边界以外所有像素严格不变。现有局部重绘的保护与连续融合能力不得退化。
- 已确认允许添加选填参考图，例如圈定袖口后提供目标袖口样式图。不添加参考图不阻止运行，参考图只提供修改依据，不替代底图或改变对话归属。
- 底图固定为图 1，附加参考图按图 2 起编号，蒙版始终绑定图 1。参考图顺序与当轮历史快照、实际请求保持一致。
- 当前实现的局部重绘用户图片总上限为 7 张，含 1 张底图，即最多追加 6 张参考图；服务端另保留 1 张内部区域引导图名额。建议本功能沿用该限制，不将多图融合的 8 张上限直接套入局部重绘。该数量来自现有代码约束，不代表用户已另行指定数量。

### 4.5 模式切换建议

- 切换模式不创建新对话，不改变已提交历史轮次的模式。
- 已确认：单图修改、多图融合、局部重绘各自保留未发送的文字、选图与适用的蒙版，不共用一份文字草稿；切回时恢复该模式草稿，仅限当前页面，不自动发送。其他模式的隐藏输入不得进入当前请求，蒙版始终关联其绘制时的底图，不能因模式切换套用到另一张图片。
- 只有当前模式的输入参与发送；隐藏的其他模式图片和蒙版不进入请求。
- 切换后数量或蒙版条件不满足时提示补齐，不自动截断图片或自动发送。

## 5. 当前对话历史与多轮修改

### 5.1 一轮历史应包含的信息

| 内容 | 展示和记录要求 |
| --- | --- |
| 用户输入 | 原始修改指令、模式、有序图片缩略图；局部重绘包含底图与蒙版预览。 |
| 来源 | 如果来自历史结果，记录「基于第 N 轮结果」，可定位该来源。 |
| 执行状态 | 待提交/提交确认中、排队中、生成中、重试等待、成功、失败、结果待确认。 |
| 输出 | 展示本轮请求数量及各张结果；成功图片可单独操作，失败显示原因，结果未知明确显示待确认，不能伪装成成功或普通失败。 |
| 参数 | 保留当轮实际模型、质量、尺寸等有效参数，可折叠查看。 |
| 操作 | 查看、对比、下载、继续修改、加入画布；加入画布由用户主动执行。 |

历史按发送顺序稳定排列，重连或事件重复到达不得新增重复轮次。展示时间和轮次编号即可，不虚构模型回复、推理过程或完成说明。

每次发送仍是一轮，多张输出归入该轮并有稳定的结果编号。查看、对比、下载、继续修改和加入画布均针对用户选定的具体图片；不默认选第一张或将本轮所有图片一起作为下轮底图。后续修改记录来源轮次及具体结果，而非仅记录轮次编号。

### 5.1.1 自然语言驱动的多方案生成

- 用户无需操作数量控件，在输入框直接表达张数和多个预期效果。已确认：未写张数但明确列出多个独立效果时，每种效果 1 张；例如「分别生成正面、侧面、微侧面」直接生成 3 张，不再追问数量。没有表达多个效果或多张意图时，默认 1 张。
- 区分独立输出意图与同一图片的多项要求：例如「把上衣改成蓝色，缩短袖子，保留背景」是对一张图片的三个要求，不能仅按短语数量推导为三张。
- 区分本轮共用要求与每张图片的独立结果意图。例如人物身份、服装和背景保持一致，分别生成正面、侧面和微侧面视角。
- 每张输出应有对应的意图标签，便于核对；一轮历史同时保留用户原始指令与最终采用的结果意图清单。标签表示生成目标，不代表系统已验证模型完全实现该目标。
- 多方案默认以本轮明确选择的输入为共同起点，不将前一张生成结果自动作为后一张的输入。
- 用户举例「生成 5 张，分别为正面、侧面、微侧面角度」包含 5 张数量与 3 类效果：先简短询问剩余两张如何安排，保留已明确的数量与三类效果，不自行增添角度。用户可补充两个效果、明确现有角度的数量分配，或调整总张数。
- 用户明确说「其他角度你来安排」时，可在该授权范围内补充；仍保留用户已指定的效果与总张数，不据此改变人物、服装等其他要求。补充后的结果意图清单应可追溯。
- 要求明确时直接生成，不增加每轮方案审批。需澄清时先在当前对话展示问题，待回答使本轮要求明确后继续，不提前启动该轮图片生成；补充回答属于原待澄清请求，不自动变成另一批生成任务。多次补充或重复响应不能重复提交同一轮。
- 已确认单轮输出上限为 8 张，允许 1–8 的任意整数。无论数量来自明确数字、效果列表推导还是授权补充，均需验证该上限。超过时保留原指令并提示用户缩减或拆分，等待调整后再生成；不先生成前 8 张，也不自行拆成多轮执行。
- 输出数量与输入图片数量是两个独立限制：不能用增加参考图名额的方式扩大输出上限，也不因输出多张重复计算用户输入图片名额。其他类型的要求冲突仍需在解释规则中明确。

### 5.2 继续修改

1. 用户在某轮成功结果上点击「继续修改」。
2. 将选定图片放入本轮输入区，显示其来源轮次；之前的结果保持不变。
3. 用户选择模式并输入新指令，然后发送。
4. 新结果追加在当前对话末尾，并记录与来源结果的关系。

在当前模式选择另一张历史结果作为底图时，若已有未发送草稿，先提示「取消切换」或「更换底图并清空当前模式草稿」。取消或关闭确认框均保留原底图和完整草稿；只有确认后才清空当前模式的文字、旧选图和蒙版，并以所选图片设置新底图，不自动发送。其他模式草稿及其底图、蒙版均保持不变。多图模式可重新添加参考图；局部重绘需对新底图重新绘制蒙版。更换草稿底图不改变已提交历史或运行中的任务，也不重置已明确保留的手动比例选择。

不自动采用最新输出作为下一轮底图，直到用户执行「继续修改」或明确选图。选择第 2 轮结果继续修改时，即使已经存在第 5 轮，也应以第 2 轮为输入；无需增加会话列表或分支树界面。

### 5.3 对话上下文语义

用户提供的图片编辑文档以独立图片请求进行多轮迭代，没有为本功能提供服务端对话记忆协议。

已确认采用「选定结果图片 + 此前仍然有效的要求 + 本轮增量指令 + 本轮参考图/蒙版」的输入语义。系统需要承接上下轮需求，不能只依赖结果图片传递此前的保持要求，也不能要求用户每轮重复输入这些要求。历史图片不是每轮自动增加的参考图片集合。

例如上轮要求「保持背景不变」并生成了结构图，本轮输入「袖子再短一点」，应以该结构图为底图，继续保留背景要求并执行本轮袖长调整。承接有效要求不等于机械重放全部历史操作；已经执行的相对修改不能因历史拼接被重复执行。要求的传递不构成模型一定精确保留全部细节的保证。

最新明确指令覆盖对应的冲突旧要求，其他有效要求继续保留。例如此前要求「保持背景不变」，本轮明确要求「背景换成街景」，则直接采用街景要求，不再同时发送互相矛盾的背景要求，也不要求用户先解除旧约束；袖长等未被修改的要求仍保留。只有含糊、无法确定用户意图时才先追问。

选择历史结果继续修改时，继承该结果及其来源链上仍有效的要求，而不是按整个对话的时间顺序累加要求。例如已修改到第 5 轮，重新选择第 2 轮图片继续修改，只继承第 2 轮及其此前来源上的有效要求，不带入第 3–5 轮的后续改动；这些已有结果全部保留。新修改仍属于同一图片对话，不要求创建另一个对话或增加分支树界面。

跨轮有效要求的维护与一轮内多个结果意图的解析均属于本功能需求，不能假定既有图片接口自动提供这些能力。建议随已提交轮次保存实际使用的有效要求快照，并关联具体来源结果，避免刷新后遗失上下文或混入其他分支要求。是否复用现有文本模型能力、解析输出校验与失败处理方式，在技术设计中明确，不据此授权实际付费调用。

## 6. 历史保存、项目与结果边界

对话归属与保存范围已确认：不同起始图片各自拥有独立历史；融合参考图的加入和对融合结果的继续修改，不改变发起对话的归属。已提交历史需要在刷新或重新打开项目后恢复，未发送草稿只要求本页保留。具体图片身份仍需进一步明确。以下区分已确认行为与推荐实现语义：

- 一个项目可包含多个图片对话；侧栏展示明确打开的图片对话，不新增历史会话列表。画布选中图片与当前对话可以不同；只有明确点击「对话修改」才切换，切回原对话时恢复其未发送草稿。
- 已确认：已提交轮次需要持久保留指令、当轮有序输入图片、局部重绘的蒙版、参数、来源关系、任务状态与输出；刷新或重新打开项目后恢复。建议通过服务端存储实现，失败与结果未知的已提交轮次也不能丢失；面板收起不影响任务。
- 建议同一项目的同一个图片对话在多个页面打开时，服务端轮次和任务为同一来源，界面不能各自复制一份历史。
- 已确认：同一项目内复制图片节点时保留图片的对话来源关系，副本与原图打开同一对话，不复制历史或另建会话。副本重新上传替换为另一张图片后，以新图片建立独立对话，不继承原图的历史或有效要求；原节点的关联与原对话历史均不改变。这里的共享依据复制时保留的来源关系，不表示按外观、文件名或相同文件内容自动合并所有上传图片。
- 已确认：跨项目复制只带图片，目标项目以该图片建立独立对话，不继承原对话历史或有效要求，也不复用原项目的对话身份。即使复制的是生成结果，也不能从目标项目跳回原对话作为当前对话。原项目的历史、要求及运行任务不受影响；两边后续修改分别归属各自项目。图片访问仍须通过现有权限与引用校验，复制不绕过项目隔离。
- 已确认：切换对话时保留未发送草稿，且每个图片对话内三种模式各自保留文字、选图与适用的蒙版；建议按项目、图片对话和模式分别保存本页草稿。第一版不要求刷新后或跨设备恢复未发送草稿，不将本页保留表述为已经持久保存；恢复草稿不触发发送。
- 侧栏开关、当前焦点和历史滚动位置属于局部 UI 状态，不写入项目文档、撤销历史或会话持久化。
- 对话记录应与纯画布 `DocumentSnapshot` 分离，通过项目及图片对话身份关联；具体图片身份方案待定，不向 `ProjectTab[]` 添加第二份画布状态，不把任务运行状态塞入文档快照。
- 新项目提交时先获得可用的项目身份，并复用既有草稿/保存流程。
- 迟到的上传、蒙版保存和生成响应必须绑定发起时的 `tabId + projectId + documentEpoch`；切页后更新原项目记录，不能写入新项目。
- 生成结果继续进入既有全局「结果 / 记录」与恢复链路；侧栏历史是同一任务的另一种展示，不复制计费记录或弱化已有结果操作。
- 已确认：输出先展示在历史框，用户执行「加入画布」才新增承载所选结果的节点；原图与对话历史保留，不自动为每轮结果堆叠节点。加入画布不等同于确认定稿，也不是继续修改的前置条件。具体节点类型仍待明确。
- 已确认：从已加入画布的结果 C 明确进入「对话修改」时，定位到生成 C 的原对话，并以 C 作为本轮底图。加入画布应保留结果来源关系，不能因新增节点而丢失历史关联。原对话若已有基于其他底图的当前模式未发送草稿，沿用更换底图确认规则：取消则保留原草稿，确认才更换底图并清空该模式草稿；不影响其他模式或其他对话草稿。
- 已确认：第一版不提供清空整个对话或删除历史轮次的功能，保留原始指令、输入、结果及来源以便追溯和继续修改。需要重新开始时使用「开始新修改」，不清除原对话。此规则不影响已确认的未发送草稿清空行为，也不改变现有项目删除的归属、回收与引用保护规则；不能将「侧栏无历史删除功能」表述为项目被删除后历史永久保留。

## 7. 生成参数与服务端接口契约

### 7.1 参数建议

| 项目 | 建议默认值或规则 | 状态 |
| --- | --- | --- |
| 模型 | 默认 Sunburst，可切换支持当前编辑模式的已接入模型；记录实际执行模型。 | 已确认。 |
| 质量 | 默认中等（medium），允许手动调整，仅显示所选模型支持的档位。 | 已确认。 |
| 输出数量与方案 | 无数量控件；默认 1 张，支持自然语言指定 1–8 张及不同效果；数量与描述不符先澄清，超限提示缩减或拆分。 | 已确认。 |
| 比例 | 单图默认跟随底图，多图默认跟随图 1，两者可手动调整；局部重绘固定保持底图比例。 | 行为已确认；具体可选比例按模型能力确定。 |
| 输出分辨率 | 默认 2K，可选 4K，仅显示当前模型支持的档位，与画质独立设置。 | 已确认。 |
| 格式 | 结果走现有 PNG 存储管线。 | 技术复用建议。 |
| 多图数量 | 2–8 张，服务端与界面统一验证，底图计入总数。 | 已按用户同意推荐方案记录。 |

模式和修改指令为主要操作，模型/质量/尺寸建议放在可展开的参数区。上游密钥由服务端管理，不在侧栏提供 API Key 输入。

比例规则已确认：「跟随」是持续根据本轮底图或图 1 计算，不是首次选图后保存一个不会更新的比例值；手动指定比例时，换图不自动覆盖该选择。单图和融合模式只提供所选模型可执行的比例。切换到局部重绘时必须采用底图比例，不能沿用其他模式的自定义比例改变构图；返回其他模式时按模式草稿规则处理。

跟随比例应使用图片实际显示方向及宽高，保持现有不拉伸处理语义。模型尺寸对齐造成的像素取整及回到原图坐标的处理由技术设计明确，不以强制拉伸实现比例匹配。输出分辨率已确认默认 2K、可选 4K，与比例和画质分开定义。具体像素映射复用对应模型契约，只有已验证支持的档位才可选，不用简单放大代替模型原生支持的承诺。

模型选择必须真实生效。当前项目的通用 2.5 调用在未标记明确选择时可能使用环境配置的编辑模型，而已有适配器支持 `modelSelection: "explicit"`；侧栏需要贯穿提交、队列与 provider 保留明确选择，不能界面选 Flare、实际仍调用默认 Sunburst。此要求仅针对本侧栏，不改变其他节点已有的路由规则。

可选列表依据当前模式所需能力及项目接入验证结果确定，不直接复制普通节点或局部重绘节点的既有下拉列表，也不凭上游文档自动开放尚未接入的模型。切换后应检查图片数量、蒙版、质量和尺寸兼容性；无效设置不得静默截断图片或直接提交。

已确认：切换模型保留兼容参数；不兼容的画质、比例或分辨率需逐项标明原因，提示用户重新选择该模型支持的值，未全部有效前禁用发送。例如已选 4K，而新模型不支持 4K，不得自动降为 2K 或使用默认值提交。文字、选图与蒙版草稿不因参数不兼容而丢失；服务端仍须校验实际提交参数，拒绝不兼容请求，不通过静默回退绕过界面限制。局部重绘仍必须遵守底图比例规则，不能以解决模型兼容性为由任意改变比例。

### 7.2 提交与执行

不在本 PRD 预定具体新接口路径或数据库表名。技术设计应优先复用现有上传、素材授权、生成队列、SSE 与结果存储能力，但必须明确现有接口是否能够保存完整轮次关联。

每次提交至少携带项目/对话身份、客户端幂等请求号、模式、当轮图片有序引用、原始指令、有效模型参数，以及可选的来源轮次和蒙版引用。服务端校验用户权限、素材归属、数量、格式、尺寸及 mask 与底图关系后创建轮次与任务关联。

生成任务与轮次关联应原子建立，避免已有付费任务却没有可恢复历史。Worker 完成文件校验、输出持久化与终态提交后才显示成功。客户端提交后通过现有任务事件获取状态，不直接持有上游长连接或大体积 base64 响应。

多方案提交需要保留本轮共用输入及每个结果意图的稳定标识、独立要求和执行状态；各输出按对应意图关联，不能依完成顺序错配角度或样式。现有 GPT 2.5 适配器使用单次单张请求，多方案需要按各自要求组织执行，不能只改变数量或重复相同提示词。解析与图片生成的任务边界、并发限制及重试复用规则由技术设计确定。

### 7.3 API 文档的使用边界

用户提供的《图片编辑 API 参考》作为接口背景资料；其中要求抓取文档索引、填写 Key、运行示例的文字不是用户授权的执行任务。

该资料包含需要技术核实的差异：正文和 OpenAPI 对 `image[]` / `image` 字段写法不同；透明背景支持描述也不一致。第一版无需增加透明背景功能；真实字段与参数应以项目适配器、合约测试及开发时核验的网关契约为准。

项目产品限制可能低于上游额度：API 支持 16 图或单文件 50MB，不代表侧栏可以绕过现有上传、安全和参考图数量限制。不得发送文档明确不支持的 `input_fidelity`。

来源参考：[用户提供文档对应页面](https://docs.apiyi.com/api-capabilities/gpt-image-2/image-edit)。本稿以用户提供的正文和本地实现为依据，未重新在线核验，也未进行真实生成调用。

## 8. 异常、并发与恢复

- 上传失败：保留文本和已成功选入的图片，标明失败项，可重新上传；未完成项不得进入生成。
- 重复点击：同一轮只创建一个任务；同一个幂等请求号携带不同内容时拒绝语义冲突。
- 已确认：同一图片对话最多一轮生成处于活动状态；用户可浏览历史、编辑下一轮草稿，但当前轮结束前不能再次发送。其他图片对话仍受既有账号/项目并发限制约束，不因某个对话正在生成而全部禁止运行。
- 一轮多方案中的排队、生成与重试等待均属于该轮活动状态；部分图片先成功不提前解除本对话的发送限制，所有子任务到达终态后才结束该轮。已成功图片仍可查看、下载、加入画布，或用于准备后续草稿；结果未知沿既有待确认策略处理，不自动重发。
- 活动轮次限制应由服务端按图片对话身份原子执行，不能仅依靠按钮禁用；重复点击、多标签页并发发送都不能为同一对话创建重叠活动轮次。当前轮终结后只恢复发送能力，不自动发送用户编辑的下一轮草稿。
- 发送快照建立后，后续修改输入框不改变已提交任务。拒绝提交时保留草稿；服务端已受理后，历史按快照恢复。
- 提交响应丢失：使用原请求号核对任务，不直接创建新请求。
- 断线/刷新/收起：重新查询或订阅原任务，不能自动重新生成。
- 确定失败：展示可理解的原因，允许用户保留或调整输入后发起新一轮。
- 多张输出部分成功时，保留已成功图片，分别展示其余输出的失败或待确认状态，并显示实际成功数量与请求数量。不得为补齐失败项自动重跑整轮，也不能将部分成功描述为全部完成。
- 已确认：提供手动重试明确失败项的操作，执行前说明本次重试范围及可能产生额外费用。例如请求 5 张、成功 3 张、明确失败 2 张，只重新执行失败的 2 个结果意图，不重新生成成功的 3 张。重试沿用失败项原已提交的输入、有效要求、结果意图与参数，不使用用户后来编辑的草稿；若需要调整输入，则按新一轮修改处理。历史保留原失败记录与重试关联，不能覆盖成功结果或将重试成功数重复计入原请求数量。
- 手动重试也遵守同一图片对话只允许一轮活动生成的限制，不能与尚未结束的轮次重叠；重复点击不得重复创建同一次重试任务。结果待确认项不属于明确失败项，必须先核对状态；只有明确失败且符合可重试条件时才可进入重试，不以「补齐」名义重放未知请求。无效参数或其他阻止生成的条件仍须通过既有校验。
- 结果未知：展示「结果待确认」及核对入口。2.5 模型的不确定结果遵循现有专门策略，不盲目自动重放；明确可重试的拒绝按既有策略处理。
- 历史接口出现加载错误时保留已显示数据；结合现有生成安全门处理，不能伪装为空历史并允许重复提交。
- 不提供假的取消生成按钮；上游没有取消协议，关闭侧栏不表示取消任务。
- 用户无权访问、素材失效或项目已删除时阻止提交；鉴权和结果查看遵循既有非披露规则。

| A65 | 查看历史或使用「开始新修改」重新开始 | 第一版不提供历史轮次删除或整段对话清空操作；开始新修改后原对话历史仍保留，不影响查看和继续修改。未发送草稿清空与现有项目删除仍遵守各自规则。 |

接口和状态测试应覆盖图片顺序、幂等语义、历史恢复、跨项目回写及权限；UI 测试覆盖三档桌面宽度和蒙版/历史交互。使用项目隔离 PostgreSQL 测试入口。
