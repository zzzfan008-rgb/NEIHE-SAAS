关于 Pro 输入图被拦（blockReason=OTHER）的处理建议

先说结论：这次是原厂在生成前对输入图做的检查，拦的是图2 人物板那张原图的像素，和提示词、图片数量、请求结构都无关。把图2 重新保存一次后，完整的 6 图请求在 Pro 上 2/2 正常出图，人物、姿势和全部穿搭都对。所以一二阶段合并成一个节点的思路没有问题，可以继续用。

一、人工操作（画布里手动出图时）

1. 参考图先「另存一次」再上传：用任意修图工具（系统自带的预览、PS、美图都行）导出成 JPEG，质量选 90~95，长边不超过 2048px。肉眼看不出变化，但能避开这类对原图像素特别敏感的拦截。
2. 大图先缩小：场景图、穿搭图原图长边在 3000~4000px 左右，缩到 2048px 以内不影响出图效果，上传也更快。
3. Pro 返回 OTHER 的判断方法：如果几秒钟就返回失败、没有出图，基本就是输入图被拦。先把最近新加的那张参考图重新导出一次再试；还不行就逐张去掉，找出是哪一张。
4. 人物板尽量用「全身多角度」：我们测试中，四宫格里只保留面部特写那一格时仍然会被拦，拆开后单独的正面全身图可以通过。如果某张人物板反复被拦，可以先只用正面全身图。
5. 如果某张图实在过不了 Pro，这一步可以先用 gemini-3.1-flash-image 出图，它对这类输入更宽松。

二、代码（工程化自动处理）

1. 所有参考图发送前统一预处理，不单独针对某张图：
   转 sRGB → 按 EXIF 摆正 → 长边限制 2048px → 重新编码 JPEG q90~95 → 去掉元数据。
   这样请求体会小很多（这次原请求有 4.6MB），上传更快，也能减少 OTHER 拦截。Node 示例：

import sharp from "sharp";

async function normalizeRef(buf) {
  return sharp(buf, { failOn: "none" })
    .rotate()
    .toColorspace("srgb")
    .resize({ width: 2048, height: 2048, fit: "inside", withoutEnlargement: true })
    .jpeg({ quality: 92, mozjpeg: true })
    .toBuffer();
}

3. 记录排查信息：每次失败都记下 responseId，以及每张参考图的 hash 和尺寸。出现问题时可以直接找到是哪张图，也方便把 responseId 发给我们协助排查。
4. 被拦的请求一般几秒就返回，自动重试一次对整体耗时影响很小。
