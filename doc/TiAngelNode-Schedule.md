## 1. 结论与假设

单名熟悉本仓库的全栈工程师：工程开发与自动化验收约 **12–17 个工作日（含缓冲）**，约 2.5–3.5 个五日工作周。另行授权的真实生成效果验收增加 **1–2 个工作日**；端到端合计约 **13–19 个工作日**，不含等待授权/外部服务及发布部署。

这是基于任务复杂度的人工工作量估算，不是运行测量、Codex 墙钟承诺或已确定交期。AI 可辅助编码，但不能按固定倍数缩短集成、浏览器检查和效果评审。

- 1 人日按约 6 小时有效工程时间估算，包含任务内自测和一般沟通。
- 假设需求不增加，已有 Node ≥22.20、pnpm、Docker、隔离 PostgreSQL 和浏览器测试环境可用。
- 不含旧项目已有失败的无关修复、GitNexus 门禁迁移、生产服务操作和新模型接入。
- 真实生成需用户提供可用素材并确认费用/调用量；模型效果不足不能保证在缓冲内解决。
- 不指定日历开始/截止日期；D1 是用户授权开发且环境就绪后的首个工作日，不是本文创建日。

## 4. 并行方案与关键路径

默认单人串行。若实际安排两名熟悉项目的工程师，T01–T03 契约稳定后，可将服务端 T04 与 UI/Three.js T05–T06 分开。共享 Store、schema、DAG 保持单一集成人；联调与最终验收仍须串行。

双人日历周期可初步估为 **9–12 个工作日（含协调与缓冲，不含 T09）**，总工作量不会减半；这不是默认资源承诺，也不代表已创建任何代理或任务。关键路径是契约/持久化 → 端口计划 → 执行确认及控件两支完成 → 模板 → 综合回归。

## 5. 可能改变排期的事项

| 风险 | 发现时点 | 处理与排期影响 |
| --- | --- | --- |
| 旧运行缺少可校验输入指纹 | T00/T04 | 先验证能否补既有元数据；如需主要方案变化，暂停该分支对齐并重新估算 |
| 图片边被现有通用逻辑自动透传 | T03 | 补类型化边回归；计入 1–5 日缓冲，不移除原图 |
| 3D 遮挡、背面拖动、roll 方向错误 | T06 | 用几何测试和真实浏览器重现；不能只交静态图 |
| 本地门禁依赖 GitNexus | 开始即已知 | 禁止运行，保留独立测试证据并明确完整门禁不可用；迁移另排 |
| 模型对背面或大角度遵循不足 | T09 | 记录限制，用户决定继续研究或收窄范围；不承诺有限返工必能解决 |
| 授权、素材、密钥或服务不可用 | T09 前 | 等待时间单独记录，不伪计为开发完成 |

T00、M2、M3 后分别用实际耗时更新剩余估算；先核对原因和范围，不直接改已确认需求。完成代码、验证真实效果、发布上线是三个独立状态。
