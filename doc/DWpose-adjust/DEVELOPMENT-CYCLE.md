## 1. 排期口径

- 当前状态：P0/M0、P1/M1、P2 已验收；P3/M2 聚焦验证有通过记录，六项额外 1024px E2E 目标已完成 baseline 对照、修正与复验（含 1024/1280/1440 人物板尺寸和鼠标交互）。P4 交互提案已确认并完成实现/M3 聚焦验收；P5 集中回归与范围内 M4 交付验收已完成。未迁移的 GitNexus gate、真实付费模型质量和无筛选全量浏览器 E2E 明确不在本批覆盖。
- 估算基线：1 名熟悉当前项目的开发者，按每天约 6–8 小时有效研发时间顺序推进，不假设多代理并行。
- 基础周期：16 个工作日；预留 3 个工作日缓冲，预算合计 19 个工作日，约 4 个工作周。
- P0 完成后复核估算：契约和样本没有引出新增跨域或依赖范围，原基础周期保持 16 天；P0 计入 2 天，P1–P5 尚余 14 天，另留 3 天缓冲。
- 各阶段包含本阶段测试和修复；P5 是集中集成回归，不是首次开始测试。
- 用户确认等待、授权澄清、环境修复、真实模型付费验证、提交与部署等待不计入有效研发日，应单独记录。
- 此为工程估算，不是 AI 执行时长承诺。DWPose 结构化协议和固定样本已冻结；代码阶段仍须实测依赖、模型环境和接口行为。
- 不新增依赖。2D 使用 React-Konva，3D IK/相机投影使用独立 TypeScript 数学和 Canvas；不引入许可不明的上游源码。

## 4. 风险对排期的影响

| 风险 | 调整策略 |
| --- | --- |
| COCO/OpenPose 的点序和手脸格式差异超出样本覆盖 | 优先使用缓冲完善映射和往返验证，不静默裁剪点集 |
| 旧 Python 服务或测试环境不可用 | 保留旧功能，记录环境阻塞；恢复后继续对应阶段，不用假数据冒充服务通过 |
| IK 退化输入或投影恢复不稳定 | 不越过 M3；使用缓冲修复，不宣称可由 2D 唯一恢复深度 |
| 三宽度布局/React Flow 事件冲突 | 修复新增编辑器范围；既有问题需独立证据，不能掩盖新回归 |
| 上游许可不清 | 按独立实现继续；若改为直接移植，需重新确认授权和估算 |
| 实施中发现需引入新依赖或扩大范围 | 暂停相关部分，说明必要性、影响与排期变化，等待确认 |
| 现有人物板改动与目标文件重叠 | 保留当前改动，在现有基线上编辑和复核，不重置工作区 |

缓冲消耗完仍有阻塞时，重新估算并报告，不通过删除验收项目来保持日期。
