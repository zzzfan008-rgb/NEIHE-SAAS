# NEIHE-无限画布 项目宪章

## 核心原则

### I. 意图优先的直接操作

每个画布核心操作都必须通过直接、可预期的操控反映用户的可见意图。选择、移动、
缩放、平移、调整大小和创建必须提供即时反馈，且不得意外破坏用户当前的位置、
选区或焦点。任何破坏性或大范围变更都必须可通过撤销与重做恢复。输入行为、焦点、
选区及边界情形必须在实现前明确写入功能规格和验收场景。

理由：无限画布只有在空间操作值得信任、误操作可恢复时，才能让用户安全地探索和创作。

### II. 单一空间模型

持久化内容必须使用唯一的标准世界坐标模型。视口坐标、屏幕坐标和世界坐标之间的转换
必须显式、确定且可独立测试。渲染、命中测试、选区边界、吸附、导出及协作逻辑必须源于
同一模型。视觉优化不得暗中改变持久化几何数据，也不得引入第二个状态真相源。

理由：统一空间模型可防止累积误差、缩放相关缺陷以及不同输入方式和功能之间的行为不一致。

### III. 数据默认可恢复

用户创作的内容必须在可预期故障、页面刷新和会话中断后按功能规格中的持久性要求存活。
持久化格式必须有版本；不兼容变更必须提供通过测试的迁移，或明确的导出与恢复路径。
每个可变命令必须定义撤销语义。错误处理必须保留最后一个已知正常状态，并向用户说明恢复结果。

理由：画布承载的通常是无法重现的思考过程，因此数据完整性高于便利性或实现速度。

### IV. 关键行为测试先行

坐标转换、命令历史、持久化、迁移及其他核心状态行为的测试，必须在对应生产实现之前编写，
并必须先因预期原因失败，然后再按红-绿-重构循环完成实现。交互边界与存储合约必须有集成测试。
任何例外都必须在实施计划中记录替代验证方法，并获得审查者明确批准。

理由：空间数学和状态转换中的错误会迅速放大，通过可执行合约预防比在视觉异常后调试成本更低。

### V. 性能、可访问性与简洁性

可能影响渲染、输入延迟、文档容量或启动时间的功能规格，必须定义可测量的性能验收标准。
核心工作流必须支持键盘操作、呈现明确焦点，并在使用动画时尊重减少动效偏好。实现必须选择
满足当前需求的最简单设计；没有已记录的具体需求，不得引入投机性抽象、依赖或平行状态系统。

理由：响应速度和可访问性属于产品正确性，而简洁性使这些要求在画布持续扩展时仍然可维护。

## 产品与技术约束

- 除非功能确实依赖某个框架，产品行为必须独立于具体渲染或 UI 框架进行定义。
- 持久化用户内容在存储代码合并前，必须明确数据模式、所有权边界和兼容性策略。
- 外部依赖必须有明确用途、可维护性信号、兼容的许可证和可执行的移除路径。
- 诊断数据默认不得包含画布内容或个人数据。若需收集，必须有明确功能需求和用户授权流程。
- 安全、隐私和可访问性要求必须进入相关功能规格和验收标准，不得只留在实现备注中。

## 开发流程与质量门禁

1. 任何功能必须依次经过需求规格、必要的霄清、实施计划、依赖有序任务、实现与验证。
2. 功能规格必须包含可观察的验收场景，并识别数据丢失、空间一致性、可访问性和性能风险。
3. 实施计划必须记录状态模型、坐标系影响、持久化影响、测试策略和已批准的宪章例外。
4. 代码审查必须在合并前核验验收场景、自动化测试、数据迁移安全性和宪章合规性。
5. 只有必需测试通过、用户可见行为已验证，且相关文档或迁移说明已更新，变更才算完成。
6. 无法移除的复杂性必须在计划中说明已考虑的简单方案，以及拒绝该方案的具体需求。

## 治理

本宪章优先于项目的非正式惯例和实现便利性。修订必须提供书面理由、对活跃功能规格和
已交付行为的影响评估，并明确变更版本。

宪章版本遵循语义化版本：删除原则或不兼容地重新定义治理要求时升级主版本；新增原则、章节或
实质扩展要求时升级次版本；不改变义务的澄清、措辞或拼写修正时升级修订版本。每份功能计划和
代码审查都必须包含宪章合规检查。经批准的例外必须记录受影响条款、负责人、原因、范围、
到期条件和补救计划。功能改变持久化数据、交互语义或核心架构时，必须重新审查合规性。
